# 25. Agent Sandboxing

A coding agent runs commands with its user's privileges on input it did not write. This document covers what bounds it: the isolation it runs inside, the modes that remove the prompts, how untrusted input is kept away from what an injected instruction could use, and what an agent step in CI is allowed to hold. How a credential reaches a process at all is [13-secret-management.md](13-secret-management.md).

## Core Rules

- Bound an agent by filesystem and network isolation together, and treat permission prompts and auto mode's classifier as layers inside that boundary, never as the boundary (§1).
- Count a boundary only for what it encloses — the OS sandbox covers Bash alone, so it bounds a session whose other tools still pass prompts, and a git worktree covers nothing — and treat a lane the harness runs unattended as a session under these rules (§1).
- Run a mode that removes every check — bypass, not auto mode, whose classifier stays on the prompt side (§1) — only inside a container or VM that nothing reopens to the host, and review what the agent wrote into the bind-mounted workspace before running anything from it on the host (§2).
- Inject each credential into the process that uses it rather than into the agent's own environment, and keep one that must be out of reach outside the boundary, behind a proxy (§2, → [13-secret-management.md](13-secret-management.md) §7).
- Give an agent session at most two of untrusted input, reachable secrets or private data, and a tool that changes state or communicates externally; with untrusted input present drop one of the other two, and split a task that needs all three or put it behind human approval (§3).
- Treat a subagent's summary of untrusted text as untrusted, and pass an action taken on it through a check or an approval first (§3).
- Give each CI job that runs an agent only the token scopes, persisted credentials and secrets its step uses, declared in the workflow rather than inherited from a default (§4).
- Treat every CI event that carries a stranger's text as untrusted input whoever triggered the run, and on a privileged trigger never check out the untrusted head or interpolate event text into a command (§4).

## Details

### 1. Isolation before prompts

A permission prompt asks a person to judge every action, and people stop judging. Anthropic reports that "Claude Code users approve 93% of permission prompts", and describes the cause: constant approval "can lead to 'approval fatigue', where users might not pay close attention to what they're approving". A boundary set once does not depend on that attention. In Anthropic's internal usage, its sandbox — built on OS primitives, bubblewrap on Linux and Seatbelt on macOS — "safely reduces permission prompts by 84%", because actions inside the boundary no longer need asking about.

The two isolations cover each other's escape: "Without network isolation, a compromised agent could exfiltrate sensitive files like SSH keys; without filesystem isolation, a compromised agent could easily escape the sandbox and gain network access." A sandbox that allows the network freely, or writes anywhere, is one of the two halves and is not counted as isolation.

That sandbox has a stated scope: it "restricts what Bash commands can access at the filesystem and network level. It applies only to Bash commands and their child processes." Permission rules govern everything else — Read, Edit, WebFetch, MCP. So it is the boundary for a session in which those other tools still pass a prompt or a rule, and not for a session that removes the prompts (§2). It also has a door: a command that fails in the sandbox may be retried outside it through the normal permission flow — a prompt, or the classifier in auto mode — unless `allowUnsandboxedCommands` turns that fallback off. Auto mode answers a different question: in Claude Code's own comparison, the sandbox decides "what a Bash command can access once it runs", auto mode "whether each tool call runs", with "a classifier that reviews actions". Anthropic's auto-mode post measures that classifier letting through 17% of real overeager actions, and "How we contain Claude across products" calls auto mode "one layer of defense-in-depth inside a sandbox, not a substitute for one". An auto-mode session is therefore bounded the way a prompted one is — by the sandbox — and is not one of the modes §2 confines to a container; its classifier is a filter inside that boundary, not the supervision §3 asks for. Because the sandbox covers Bash only, an auto-mode session outside a container also carries permission rules for the tools it leaves out: `permissions.deny` on credential paths in the project and outside it (`Read(./.env)`, `Read(./secrets/**)`, `Read(~/.ssh/**)`, `Read(~/.aws/**)`, `Read(~/.config/gh/**)`) and `permissions.ask` on pushes and outbound fetches (`Bash(git push *)`, `WebFetch`). The home directory needs naming because the sandbox does not cover it: its "default read behavior" is "read access to the entire computer, except certain denied directories", and the documentation adds that "this default still allows reading credential files such as `~/.aws/credentials` and `~/.ssh/`" — `sandbox.credentials`, a `denyRead` entry, or `permissions.blockReadsOutsideWorkingDirectories`, which makes "the file tools refuse the paths it fences in every permission mode", is what closes it. In auto mode "explicit ask rules still force a prompt", and deny rules "block in every mode". They match the command text Claude writes, not the program — the permissions documentation lists `git -C . push origin main` among what `Bash(git push *)` does not stop, and says such a rule "isn't a security boundary around the program" — so they narrow the common path and the sandbox stays the boundary.

A git worktree is not on this list. It keeps two lanes from writing each other's files ([09-agentic-workflow.md](09-agentic-workflow.md) §2) and nothing more: an agent in a worktree reaches the same filesystem, network and environment as one in the main checkout. A lane the harness runs without a person watching is the unattended session [20-review-gate.md](20-review-gate.md) §1 describes, and every rule here applies to it.

### 2. Bypass modes and credentials

Agents ship modes that stop asking. Claude Code's `--dangerously-skip-permissions` is equivalent to `bypassPermissions` mode, which "disables permission prompts and safety checks so tool calls execute immediately", and whose documentation warns: "Only use this mode in isolated environments like containers, VMs, or dev containers without internet access, where Claude Code cannot damage your host system." Gemini CLI's reference lists `--approval-mode` ("Approval mode for tool execution. Choices: `default`, `auto_edit`, `yolo`, `plan`") and the deprecated `--yolo` ("Auto-approve all actions"). Anthropic describes skipping as "unsafe in most situations". The condition under which it is acceptable is the isolation around it, not the task's apparent harmlessness.

The container or VM runs the agent as a non-root user, restricts its egress, and mounts no host credential, no Docker socket, no `--privileged` and no host network — each of the last three reopens the host. Docker says of `--privileged`: "A container with --privileged is not a securely sandboxed process. Containers in this mode can get a root shell on the host and take control over the system." With host networking, "that container's network stack isn't isolated from the Docker host". And Claude Code's sandbox documentation warns that "allowing access to `/var/run/docker.sock` effectively grants access to the host system through the Docker socket."

Claude Code's dev container documentation states what isolation still leaves exposed. The CLI rejects the flag when launched as root. A bypassed session "can still modify any file in the bind-mounted workspace, which appears directly on your host, and reach anything the container's network policy allows", so the flag is paired with egress restrictions. The workspace is the way back: git runs the hook programs in `.git/hooks` "at certain points in git's execution", and in VS Code a task marked `"runOn": "folderOpen"` "will be run when the containing folder is opened" wherever automatic tasks are allowed. Read both — the `.git/hooks` directory and the editor's task files — before running git or opening the editor on that tree from the host. And the container "do[es] not prevent a malicious project from exfiltrating anything accessible inside the container, including the Claude Code credentials" — hence "avoid mounting host secrets such as `~/.ssh` or cloud credential files into the container; prefer repository-scoped or short-lived tokens." An organization that wants no bypass at all sets `permissions.disableBypassPermissionsMode` to `"disable"` in managed settings.

The general form is to keep the credential out of reach: "If credentials never enter the sandbox, they can't be exfiltrated, regardless of whether the cause is a user, a model finding a 'creative' path, or an attacker." Claude Code on the web applies it to git: "in Anthropic-hosted environments, git credentials and signing keys stay outside the sandbox, and a proxy authenticates on the session's behalf with scoped credentials." For an MCP server, the equivalent is injecting its credential into the server's own process rather than the agent's (→ [13-secret-management.md](13-secret-management.md) §7). That keeps it out of the environment every agent command inherits, but not out of reach: a same-user process inside the boundary is still readable from it, so a credential that must be unreachable stays outside, behind a proxy. What the agent must hold itself is scoped and short-lived.

### 3. Untrusted input

Text an agent reads can carry instructions. Meta's Agents Rule of Two states the constraint that follows: until robustness research allows prompt injection to be reliably detected and refused, an agent should hold no more than two of "[A] An agent can process untrustworthy inputs", "[B] An agent can have access to sensitive systems or private data", "[C] An agent can change state or communicate externally" within one session. When a task needs all three without a fresh session, "the agent should not be permitted to operate autonomously and at a minimum requires supervision".

For a coding agent, [A] is any text a stranger can write: an issue, a pull request's title and body, a review comment, a fetched page, a dependency's README, an artifact another workflow produced. [B] is a secret or private data within reach of a tool the model can call — a key in its environment the shell can print, a private file or checkout the read tool can open, or a logged-in CLI the shell can call (a secret manager, `gh`, a cloud CLI), which hands over what its login reaches without any secret being in the environment. [C] is push access, a write-scoped token, or any tool that can make a request. With [A] present, drop [B] or [C]; the rule allows each pair. A research session that fetches pages ([A]) and can make requests ([C]) is within it only while it holds no [B] at all — no credentials, no logged-in CLI, and no private checkout its read tool can open. An agent that reviews a stranger's pull request ([A]) in a checkout holding private code ([B]) is within it so long as it cannot push, comment with a write token, or fetch ([C]).

Most real coding sessions hold [B] and [C] from the start — a private checkout and tools that write — so the question is what happens when [A] arrives. Meta names two answers. One is supervision: the session keeps all three, and "at a minimum requires supervision — via human-in-the-loop approval or another reliable means of validation". An interactive session whose writes and sends each pass the user's prompt is this case. A session whose writes and sends do not pass a person is not, and drops [B] or [C] once it reads [A]: bypass mode, an unattended lane, and auto mode too — its classifier approves a push with no prompt and lets through 17% of overeager actions (§1), which is not a reliable means of validation. The other answer is splitting: "without starting a new session (i.e., with a fresh context window)" is the condition under which all three need supervision, so a task can move the [A] part into a session that lacks [B] or [C].

An unattended harness lane holds private code and write tools, so it holds no untrusted input: it reads no issue, no pull-request text, no fetched page and no other external document. What the work needs from outside — an official documentation page, what an issue actually says — is fetched and checked at plan time, in the interactive session a person supervises, and what reaches the lane is the brief that person reviewed ([18-work-contract.md](18-work-contract.md)). That session is the supervised case only while each of its writes and sends passes the person — it fetches under prompts, not in auto or bypass mode, and the deny and ask rules of §1 hold there too. A lane that finds it needs something external does not fetch it: it reports the criterion that needs it as failed, which halts the lane, and the plan session fetches it and puts it in the brief — a criterion known in advance to need it is a `[human]` one from the start ([18-work-contract.md](18-work-contract.md) §1, [19-evidence.md](19-evidence.md) §3). A call the lane's own code makes to the API it is being written against — [12-upstream-docs.md](12-upstream-docs.md)'s smoke test — is not this reading: the lane records what the call returned as evidence and never follows it as instruction.

Splitting moves the untrusted text, but does not clean it. Anthropic notes that "sub-agents can isolate untrusted content, returning structured facts rather than raw text up to the main agent", and in the next sentence that this "can be abused: if a sub-agent's output is treated as higher-trust than raw tool results, because such output came from 'us,' a new vector for prompt injection is introduced." A reading session's summary is still [A] in the session that receives it. What makes the split safe is that the action taken on it — the push, the comment, the request — passes a check or a person's approval first.

### 4. Agent steps in CI

A CI job holds whatever the workflow gives it, with nobody watching. GitHub's guidance is that "the `GITHUB_TOKEN` is granted the minimum required permissions", recommending "the default permission for the `GITHUB_TOKEN` to read access only for repository contents" with increases "as required, for individual jobs within the workflow file". What the default actually is depends on a repository or organization setting, so the workflow states it: `permissions: {}` or `contents: read` at the top, then per job. Once any scope is listed, "all of those that are not specified are set to `none`". An agent job that only reviews needs `contents: read` and the ability to comment, not `contents: write`. `actions/checkout` persists its token in the local git config so later steps can run authenticated git commands; "Set `persist-credentials: false` to opt-out" in every job that does not push, or the agent's shell holds that token too. Pass a secret only to the step that uses it.

Events that carry a stranger's input need their own gate. GitHub treats pull requests and their metadata as untrusted, and calls `pull_request_target` and `workflow_run` privileged — they "may have repository write access and access to referenced secrets". Of both it says: "Workflows that use these triggers must not explicitly check out untrusted code, including from pull request forks or from repositories that are not under your control. Workflows triggered on `workflow_run` should treat artifacts uploaded from other workflows with caution." `issue_comment` is privileged in the same way. The events reference gives its `GITHUB_SHA` as "Last commit on default branch", and GitHub's `pull_request_target` guidance names it among the events that run with secrets: "Any event that runs with secrets can introduce a pwn request if it checks out or downloads and executes untrusted code. For example, an `issue_comment` or `workflow_run` workflow that fetches and runs a fork's pull request code is vulnerable in the same way." Its text is written by anyone who can comment. Untrusted text reaches beyond these three privileged triggers: "For pull requests from a forked repository to the base repository, GitHub sends the `pull_request`, `issue_comment`, `pull_request_review_comment`, `pull_request_review`, and `pull_request_target` events to the base repository." Event text reaches a script safely through an intermediate environment variable, not through `${{ }}` interpolation into the command.

For a workflow triggered from a fork, "with the exception of `GITHUB_TOKEN`, secrets are not passed to the runner", and that token "has read-only permissions in pull requests from forked repositories". A private repository can turn this off: its fork policy includes "Send write tokens to workflows from pull requests" and "Send secrets to workflows from pull requests", which "Makes all secrets available to the pull request". With either enabled, a fork's pull request brings [A] into a job holding [B] or [C], and §3 applies to that job.

The Claude Code GitHub Action applies two gates of its own: on issue and pull request events the triggering user must have write access to the repository, and bot actors are rejected unless listed. Both check the actor — the person who commented `@claude` — and not the author of the issue, pull request or file the agent then reads. A maintainer asking the agent to act on a stranger's pull request is a trusted trigger over untrusted text, so that job drops [B] or [C] as §3 requires — restricted tools, or the write step split into a job that never reads the text. Widening either gate (`allowed_non_write_users`, `allowed_bots`) removes even the trusted trigger.
